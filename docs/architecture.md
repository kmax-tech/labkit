# Architecture

Where what happens in labkit: the model of rules, checks and gates, what a check is and where its test stands, the layers, who does what and where verdicts are recorded. The chain from promise to reported number stands in [chain.md](chain.md), the one home of each recurring question in [one-home.md](one-home.md), what each gate's stations call and tell in [gate-stations.md](gate-stations.md), each rule of the standard with the sites that record it and what is not settled in [rules-map.md](rules-map.md). Terms are coined in the README; the promise block in `docs/promise-block.md`.

## Rules, checks and gates

The model in one picture; each part has its home, linked below, and this section repeats none of their detail.

```
rule (the standard, LAB-nnn)
  │  held by
  ├─ a guaranteed check     mechanical, silent on a correct input    → may block
  ├─ a static-evidence check mechanical, may be wrong                → warns only
  ├─ an agent audit         a model reads registration and code      → findings a person decides
  └─ construction           the tool leaves no way to break it       → nothing to check
        │
gate: when a check runs (its station in the chain) and what its findings stop
lane: which duties a protocol owes at all (its repeat cost)
```

| Part         | What it decides                                                                                                                                                                              | Home                                                                                                            |
|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| Rule         | what the lab holds to; one id, one name, one text                                                                                                                                            | `labkit/docs/standard.md`, ledger `labkit/docs/rules.tsv` (`python -m labkit.formats.rules show LAB-nnn`)       |
| Check tier   | what supports a finding: exact, an indication, or a model's reading                                                                                                                          | `docs/promise-block.md`, "Claim and check tiers"; a gate finding carries it as `gate.GateFinding.evidence_kind` |
| Agent audit  | a model's findings, each with its subject (where the fault lies) and its rule (which rule it breaks, or `new class`); a person decides each, and a gate holds only that every one is decided | `findings.Finding`, `labkit/agents/experiment-preflight.agent.md`                                               |
| Construction | a rule no check needs, because the tool does it: `runlog` records uncommitted code (LAB-010 Commit before the run), `batch.Store` resumes (LAB-064 The pilot is resumable too)               | the tool's own module                                                                                           |
| Gate         | the order of the stations and what each holds; a finding's grade decides block or warn, the gate decides when it is asked                                                                    | [The gates in order](#the-gates-in-order)                                                                       |
| Lane         | the duties of a repeat cost: freeze, registration, which audits, provenance                                                                                                                  | `standard_contract.Lane`                                                                                        |

Two limits stand today. Every gate finding records its rule as data (`GateFinding.rule`, a `gate.RuleAssignment`), and its line cites a rule of the standard from that datum (`gate.with_rule`: `BLOCKER: <what> (LAB-nnn <its name>). Next: <fix>`), so a site's text types no citation of it; but not for every site is the rule decided: a site names a rule of the standard, a technical contract, or carries an open assignment. The counts change with every decision and are not repeated here: `python -m labkit.tools.check_inventory` computes them from the source (sites, rule assignments, the active rules a site names); the assignments still open and their grounds stand in [the open-assignments note](notes/2026-11-11-open-assignments.md). And nothing switches a check off: a rule leaves by a release on measured evidence, and comes — from the audits' `new class` findings — only with its grounds ([note](notes/2026-11-09-checks-have-no-switches.md)). `LABKIT_PREFLIGHT=skip` in a command is no such switch: it leaves out the preflight the pre-run hook would run unasked (`hook_pre_run`), visibly in the transcript, and lifts no duty — the run's start and every later gate hold what they hold.

## Checks and their tests

What a check is, how its finding names its rule, and at which layer a test stands. How this came about, with the migration's counts and timings: [the test-model plan](notes/2026-11-10-test-model.md).

**A pure check** decides one condition from typed data. Its reference form is `check_<condition>(state: AreaState, *, evidence: AreaEvidence) -> list[GateFinding]`, with smaller explicitly typed inputs where they suffice; a check of a run receives the run's records, never a directory to read. It returns `[]` on valid input, else findings with grade, rule assignment, cause, `evidence_kind`, the check outcome (`outcome`) and the way out. It opens no file and no repository, starts no process, prints nothing, raises no `SystemExit` and does not change its input; it receives no `Findings` collector and no gate-layer `Checked`. Invalid data from the caller raises a named error. The gate decides whether and when the check runs and takes its result with `Findings.take_all`. There is no check registry and no wrapper around checks.

The contract holds for validation, not for every function. An operation whose purpose is to read, write or run something stays a named reader, writer or execution boundary and is tested with its real side effects; only a condition of it that is useful on its own becomes a pure check. The pure checks today are the ones the rule tests call under `pure_call` (in `audit_binding`, `run_record_check`, `registration_hold`, `report_decisions`, `report_exploration`, `followup` and `area_state`, two functions in `protocol_history` and one in `audit_prompt`) — a part of what decides findings, not all of it. A station function that takes a `Findings` collector composes and reports, and is tested at the gate layer; a station may hand its caller what it read (the answering run, the records). The run's start refuses by its exit (`start_check`, `console`), and a few readers return the sentence of a gap for the gate to grade (`audit_gaps`). A gate's station that takes the collector is named `station_*` (`finalize.station_run_code`, `preflight.station_scope_stamp`, `registration_station.station_registration`); a `check_*` name does not by itself make a function a pure check — readers such as `code_check.check_intent_ids` read the area, and most pure checks carry other names; the finding sites, each with its function and channel, are what `python -m labkit.tools.check_inventory` lists.

**The rule a finding names** is one validated value, `gate.RuleAssignment`, of four kinds (`gate.RULE_KINDS`) — the same value in a gate finding and in an audit record's finding:

| Kind               | Meaning                                                                                                                           |
|--------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| known rule         | carries the rule id and its name as cited: `LAB-nnn` of the standard, or `CODE-nnn` of the code standard (`docs/coding-style.md`) |
| open assignment    | the rule is not decided yet; names no rule, not even a proposed one                                                               |
| technical contract | a technical condition that no rule of the standard covers                                                                         |
| new class          | the agent audit found a fault that no existing rule names                                                                         |

Recording an open assignment approves nothing. A finding passed on keeps its grade, rule assignment, evidence kind and check outcome, but for a named transformation (`tests/test_architecture.py`, `ForwardingKeepsWhatAFindingIs`).

**Where a test stands.** At each caller, test only what the caller adds:

| Layer    | What its tests establish                                                                                                       | Setup                                                                                           | Where                                                                  |
|----------|--------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|------------------------------------------------------------------------|
| reader   | conversion between file and object, the causes of a failed read, the round trip with the writer                                | a temporary file; no gate, no repository, no command                                            | the format's own test file                                             |
| rule     | one condition: grade, rule assignment and cause; the valid twin passes; `not executable` told from `violated` where it applies | typed data in memory (`tests/state_fixture.py`); no repository, no command                      | `tests/test_rules_<module>.py`, marked `pytestmark = pytest.mark.rule` |
| gate     | composition, order, withdrawal and the choice of file state                                                                    | state in memory; a repository only to test the index against the working tree; no whole command | the gate's own test file                                               |
| scenario | the state one command passes to the next, and repairs across gates                                                             | a lab repository and real commands                                                              | a scenario file, marked `pytestmark = pytest.mark.slow`                |

A condition gets its violation and its valid twin at the rule layer, once; several finding sites that share a condition share its tests. A site that only composes or forwards is tested at the gate layer and needs no twin of its own. A scenario test that repeats what a rule test asserts is removed only with its replacement named. The tests of the repository's architecture and of its ledgers are a group of their own.

Two guards hold the rule layer to its setup (`tests/check_guards.py`, each with a forbidden and an allowed example in `tests/test_check_guards.py`): the mark `rule` runs the whole test with no process started and no console command entered, and `pure_call` calls one check with no file opened, listed or stat'ed. They enforce the boundary a test exercises — not that a condition is the right one, and not purity for every possible execution. Which test reaches which finding site, and through which layer, `python -m labkit.tools.test_inventory` measures — for the gate findings and each `SystemExit` raised in the package with a string message (counted at its raise, also where a caller catches it), with the test files per site and the count of tests marked `rule`; reach is not an assertion and the mark not a proof that a test holds one condition: only reading a test establishes what it holds. The page [checks-overview.md](checks-overview.md) lists every finding site by module, without line numbers: what it tells, its grade, evidence kind and recorded rule, and the test files that reached it in the last traced run (`docs/checks-reach.tsv`). `python -m labkit.tools.check_overview` writes it and `tests/test_check_overview.py` holds it equal to the source, so a site added, removed or reworded shows as a change of that page; its reach columns are as old as the traced run.

## Layers

Each layer is a package — a folder under `labkit/` — and a module sits in the folder of its row. Imports point downward only; no module imports a layer above it, and no layer imports a tool. Tools may import any layer. The table maps modules to layers and marks doctrine ([Core and doctrine](#core-and-doctrine) says what that means); the sections below explain each layer. Every module stands in the table exactly once. `tests/test_architecture.py` reads this table and holds the imports and the folders to it — a new module, an upward import or a module in another row's folder fails the suite. The shipped assets sit beside the packages: `templates/`, `agents/`, `docs/`, read relative to `labkit.PACKAGE_DIR`.

## Public API

The layer table holds the imports inside labkit; this section is the contract outward — the names a lab repo may import and rely on, through `from labkit.run import llm, llm_backends, llm_cache, runlog, batch` and, for the four names of `labkit.checks` listed here, `from labkit.checks import recheck, prompt_check`. Everything else is internal and may change in any release with a "Breaking" entry in `CHANGELOG.md`.

**The release rule.** A name, signature or behaviour listed here changes only after one release in which the old form still works and warns (`DeprecationWarning`, named in `CHANGELOG.md` under "Deprecated"); the release after that removes it under "Breaking". A fix that makes a name do what this table says is no such change. The list starts short and grows when a lab needs a name — taking one back would break labs. `tests/test_public_api.py` reads both tables: a listed name that is gone, a signature or default that changed (for an attribute, its annotation), or a `models.toml` key that a backend no longer reads fails the suite; the contracts in the third column have a behaviour test each.

## Core and doctrine

Two kinds of module ship in labkit, and the difference decides what another lab may change.

**Core** answers what every lab must answer the same way, whatever its rules: which run made this number, from which code, data and model, under which protocol, and does the cited number match the run. Traceability — `runs`, `scope_sha`, `promises`, `answering_run`, `repo`, the run writer.

**Doctrine** is what another lab could decide differently without being less scientific: the standard and its rules, the protocol's field catalogue, the templates and skeletons, the order of the gates, the agent layer, the note conventions, the usability probes.

**The strike test.** Strike the module. Does a number become less traceable? Core. Does the lab only work differently? Doctrine.

**The import rule.** A core module imports no doctrine module; `tests/test_architecture.py` holds that against the table above, with the crossings that stand today listed by name (`KNOWN_CROSSINGS`) until they are moved (2026-10-15). The list is not extended in passing.

One crossing was added on purpose since, and stands on these terms: `start_check` → `protocol_history` (2026-10-27, `protocol_history.registration_in_commit`). The run's start refuses a first measurement at `low` whose registration HEAD does not hold — the same rule report-check holds that commit to; without it the run started and could never be adopted. It is the doctrine `start_check` already crosses for (`protocol_check.low_registration_missing`), not a new kind. It goes when the doctrine checks at a run's start leave `start_check` as a whole (a doctrine-side start gate the run writer calls); removing this one import alone would buy a second mechanism for nothing. It grants no permission for further crossings.

One stands since the link from a confirmation to its exploration: `start_check` → `exploration_link` (`linked_exploration`) refuses the first confirming measurement under an invalid link. The conditions it asks are the lab's — the two types, the adoption — so the module is doctrine, and a refusal before the run directory exists has no caller but the run's start: a doctrine check at a run's start like the ones above, leaving with them.

The area stamp of a confirmation crosses nothing for the Conclusion it follows (`exploration_state.named_state`: the runs the adopted run rests on, the adoption and the Conclusion, and no other edit of that protocol). The line grammar of a labelled field is core (`protocol_fields`: label, value, span; it reads no template), and so is the one label that stamp names (`protocol_fields.CONCLUSION_LABEL`); the catalogue — which fields a protocol owes, and whether one is filled or still the stamp's placeholder — stays doctrine and builds on those lines (`protocol_check.fields`). `prompt_check` still crosses, for the blocks under the Prompt field (`protocol_check.registered_prompt_blocks`).

**Not the house.** Doctrine ships in labkit to every lab. The house is what holds only for this author's lab — the `LOCAL` rules, the dotfiles, the German notes — and lives outside the package ([Where what lives](#where-what-lives)).

### 1 · Formats and places

`labkit/formats/` holds the file formats, their contracts, repository locations and shared technical helpers. Validation and comparison are pure: input in, result or error out. Each format reads and writes its own files; a writer names its side effect, as in `audit_records.write`. Checks return data; console output goes through `console` and `gate`.

The protocol modules separate the TOML head (`protocol_block`), promise alphabet and tables (`promises`), prose fields (`protocol_check`), git history (`protocol_history`), a protocol as one run saw it (`protocol_then`: commit, patch and recorded block — core, so that `recheck` reads a run's own text) and the report behind `protocol-check` (`protocol_report`). `standard_contract` derives the obligations of a cost lane, release or skeleton from facts the caller supplies; it reads no files.

A protocol's step (`[builds_on]`, `protocol_block.builds_on`) names the basis run the next runs build on, the occasion, the reason and every change of the registration against the basis run's own text; `protocol-fill --builds-on` writes it with the changes computed (`tools/protocol_step.py`), never typed. There is one current step: each run keeps the step it ran under in its own text, read back by the one reconstruction every consumer shares (`protocol_then.step_then`, through `as_measured`, which refuses to read a commit alone for a run whose `uncommitted.patch` is lost — for every reader of a run's own text, the registration locks included); the run record holds no basis field, and the basis is distinct from `derived_from`. The start refuses a step whose basis is no completed run of the area, a repeat or a run of another protocol (`start_check.require_step_basis`). The declared changes are held against the differences of the two own texts by one comparison shared with `[[replaces.change]]` (`protocol_history.change_list_gaps`, `step_change_gaps`): a guaranteed statement about the protocol parts only, never about code, settings or data. Finalize holds a step in an exploratory protocol (`gates/exploration_hold.py`, its station 2): for the answering run and every basis it builds on, each run's own text and step read back, each step's declared changes equal the differences of the two own texts, a later run without a step differs from no first measurement, and once the protocol adopts the run it stands as that run's text in what the number is about. Which workflow applies is the type the first measurements registered (`registration_hold.workflow`); a confirmatory protocol, and one whose first measurement's type cannot be read, keeps the first-measurement lock, step or not (docs/notes/2026-11-14-exploratory-workflow-plan.md).

A confirmation's link to its exploration (`[explored_in]`, `protocol_block.explored_in`) names the exploratory protocol by its id — in any area of the repo — and the run that protocol had adopted when `protocol-fill --explored-in` wrote the link (`tools/protocol_exploration.py`); both ids are read once, and no later check selects a newer adoption. `exploration_link.linked_exploration` is the one answer to whether the link is valid: the linking protocol is confirmatory, the id names exactly one other protocol, that protocol's first measurements registered `exploratory` (read from their own texts, `protocol_history.first_texts`), and the run is its completed measurement, no repeat, and its adopted run. It is asked where the link is written and at the start of the first confirming measurement (`start_check.require_exploration_link`, passed by no acknowledgement), and not again: from the first measurement on the link is a registration part (`protocol_history.scope_differences`), and a change of the state it names makes the confirming audit stale instead. That state is `exploration_state.named_state`: the basis (`basis_closure` — the named run, the origin runs of its inputs and, through each run's step, its basis, transitively, each with its record, its text and its outputs), the selection (the exploratory protocol's `[result] run` now) and its Conclusion. The area stamp covers exactly these (`scope_sha.exploration_basis`), so a run of the exploration outside the closure leaves the confirming audit standing; the audit is shown them with every input digest the two protocols' runs share (`audit_prompt.exploration_evidence`, `exploration_state.shared_inputs` — static evidence, shown and never a blocker). A run of the exploration's area that shares such a digest and started after the covering analysis audit began was not shown to it: report-check warns of it, one warning per run, with the audit that shows it as the way out (`report_exploration.later_use_findings`, `exploration_state.not_shown_since`; the audit's start is its attempt's in the journal) — static evidence, never a blocker and no statement that the confirmation depends on the run. A link whose id names no protocol of the repo, or several, is another finding of another kind: nothing of the basis was read, so report-check holds the release with one blocker, guaranteed and `check not executable`, at its registration station — with or without an answering run or a covering audit, and so at the adoption's check of its proposal too (`report_exploration.unresolved_link_hold`, read for a protocol by `link_gaps`); the search for shared inputs then adds no finding of its own. The link transfers no measurement value and widens no input-origin lookup; a confirmation that names no exploration is not detectable mechanically.

A declared evidence file (`[[evidence_file]]`, `protocol_block.evidence_files`) is a data or output file the audit reads in full; `protocol-fill --evidence-file` writes the table with the digest computed (`tools/protocol_evidence.py`), never typed. Three modules share it, each with one question: `scope_sha.declared_evidence_bytes` is the one read of the declared files (for the stamp, `scope_sha.evidence_file_basis`, and for the command), `scope_sha.evidence_target_outside_repo` the one rule for a path that leaves the repository, and `audit_prompt.checked_evidence_files` the one set of checks before a file is shown or declared (a file, unchanged since its declaration, UTF-8, within the limits). The table is no part of the promise block or the registration.

`runs` reads what a run directory says about itself — its config.json as one `RunConfig`, labkit's fields typed where the record is read, the experiment's own `config` free JSON, nested values handed out as copies; `answering_run` selects the run that answers a protocol. `repo` locates the repository and its protocols and runs git; `commands` holds labkit's steps as commands (`commands.Command`) and the builders of the lines a gate prints as a way out; a line of one format's own (a discussion, a restore of a registered field or of audit evidence) is built beside that format and returns a `Command` too. `digests` is the one sha256 (of bytes, of a file, over named contents); `scope_sha` computes scope hashes and audit stamps with it. `rules` holds the standard's rules and checks their references. `findings` holds audit findings as data: the auditor records them, a person decides them, and the gates check those decisions. Beside it stand the line an auditor writes (`finding_line`), the check a finding requires (`required_check`), what a limitation does to the verdicts and the Limitation line that carries it (`finding_limits`), the names and the order of the files under `audits/` (`audit_files`), the record file (`audit_records`: written, read loudly, a decision stored in place, the records of an area) and the decisions a finding allows (`finding_decisions`: what a decided status entails and owes, the digest a review binds to). `reviews` reads and writes a second auditor's verdicts on those decisions (`labkit-audit --review`): which record, what it saw, and per decision upheld, rejected or insufficient — bound to the decision as it stood.

`handovers` holds the immutable handover records, the handover block a report carries for each (one per protocol, written from the record) and the check whether a record still acknowledges its area (`handovers.acknowledgement`). Only stop/commit may acknowledge the bound evidence loss, with no result declared and no readable BLOCKER left open. Normal audit and result release keep the integrity refusal. `attempts` retains expected lost paths from those records across commits. Its journal reader and writer require every analysis/preflight start to name its promise block and protocol. Old starts lacking either binding are refused, not migrated; reviews bind their own inputs separately. A failed file no journal attempt names remains visible without an invented start. Contract and format boundary: [audit journal bindings](notes/2026-11-03-audit-journal-format.md). Contract and limits: [handover recovery](notes/2026-10-27-handover-recovery.md).

`evidence` holds what committed evidence may become: a record changes in its findings' decision lines alone and keeps each decision a later one replaces (`decision_history`, the entries a commit holds stay), another audit file never, a closed run never; a version back as labkit first committed it is no change. Its witnesses are git's — the tree or the index against HEAD (the hooks; `change_blockers` for every release that reads an area's records: report-check's first station, an exploration's registered report, a replacement's predecessor in another area, `labkit-next` before a handover), at the stop also the session's commits against their parents and HEAD's reflog — so every change it names is undone from git, and a handover does not acknowledge it. Contract and limits: [evidence changes](notes/2026-10-28-evidence-changes.md).

The remaining helpers have narrow responsibilities. `files.write_atomic` writes one file whole or not at all. `shell.segments` reads a shell line as simple commands, respecting quotes and excluding heredoc bodies; hooks and transcript readers use the same parser. `console` provides command exits and refusals: usage errors go to stderr, findings to stdout, and a reader closing the pipe exits cleanly. `gate.Findings` collects grades, formats messages and summaries, and returns failure for blockers. It can also collect findings without printing when one gate runs inside another.

### 2 · A run and its effects

`labkit/run/` records executions, manages resumable output, calls models and holds model-slot leases. A run starts in three phases, with the order and conditions visible in `Run.__init__`:

1. `start_check.prepare` resolves the parent a derived run names, the protocol binding, takes the promise snapshot and freezes the config — a reseeded repeat's seed excepted, which runlog derives under its lock (`start_check.require_valid_reseed` holds the conditions first).
2. The start checks run in this order: the registration, a reseed's conditions, a declared answer reading's conditions (`require_answer_reading`), detachment where required, the index header, for a measurement that no run of the same script is still open, data leakage and each input's origin, for a measurement the freeze gate, and the imported code. These refusals occur before the run directory is created.
3. Creation records provenance and snapshots. A repeat's draw is reserved under the index lock before its record is written. After the record, the run directory gets the start mark (`run_starts.write_start_mark`) and the area the run's start file (`run-starts/<run_id>.json`). A failure of any of the three removes the run directory; a start file that cannot be written, or exists already, refuses the start.

`provenance` gathers git state, environment, models, data and snapshots. `code_repos` records the code the run imported beyond the lab repo's commit: every git repository that holds an imported module — labkit, a framework installed editable, a topic package — with its commit, its tracked changes as a patch and its untracked imported files copied (`code.json`, `code/`). It reads at the start and again at a clean finish, for modules imported during the run; a measurement refuses to start on untracked code it cannot copy (above 2 MB). `provenance.BinaryInput(path)` explicitly marks a binary dependency in a run's `data` mapping: its bytes are hashed, `rows` is null, and dataset decoding and row-id leakage checks do not apply to that input. Ordinary dataset paths retain those checks; one that is not UTF-8 text is refused with a decode error naming the key, the file and this wrapper (`provenance.BINARY_INPUT_WAY`). The decode decides, not the file type: a binary file whose bytes happen to decode is read as text, so a binary input is declared, never recognised. The local apply template marks its declared predictor artifacts this way; the prepare stamps and AGENTS.md name it where they ask for every file a run reads. `runlog.RunOutput(path, run=RUN_ID)` names the run of the same area that wrote an input file, and composes with the handling as `runlog.RunOutput(provenance.BinaryInput(path), run=RUN_ID)`; `provenance.declared_input` is the one unwrapping of a `data` value, so a file is digested, counted and leakage-checked alike with and without it, and `RunOutput(RunOutput(…))` or `BinaryInput(RunOutput(…))` is refused naming the key. `input_origins` decides each input's origin at start among the completed runs of the area whose `outputs.json` holds that path with that digest: one such run is the origin, several refuse the start until the script chooses one, a chosen run that is not such a run is refused, and none is a plain input without origin. A repeat is an eligible origin; adoption stays with `runs.unreportable`. Each input's entry in `config.json` records the decision (run schema 5): `origin_run` (null for a plain input), `origin_chosen`, and `origin_unreadable_runs`, the area's runs whose record did not read when the origin was decided without a choice, each `{"run", "cause"}` (`runs.UnreadableRun`) with the cause `missing` (a record file not found), `access` (could not be opened — not damage), `malformed` (the record or outputs file is not what labkit writes; also a `schema_version` that is no version) or `other_schema` (a record of a schema version this labkit does not read, named neither older nor newer); `runs.RunConfigError.cause` and `RunDir.error_cause` carry the kind from the reader on, `runs.RECORD_CAUSES`. These are skipped records, not sources: whether one of them wrote the file cannot be told, and the start warned of it once, grouped by cause. `runs.data_entries` reads every entry with all three fields or refuses it, so a record that lost its origin never reads as a plain input; the origin's own `repeat_of` stays in its record. `runlog` writes the run and index; `runlog_command` implements the console command; `detached` keeps the record of a command `runlog start` detached, locked while the command runs, with the exit status its supervisor writes, so `runlog AREA --wait` sees it before its run opens a record and fails on it when it ended without one. `batch` manages resumable output. `lanes` is the run mechanics of the stamped two-lane judge — jobs per item and lane, batches, resume, the probe, the balance, the area's command line — doctrine, since the two lanes and the probe policy per tier are how the lab chooses to measure; the area's `01_measure.py` keeps the prompts and the formulas, which the audit reads. `profile` is the data profile per gold class that the prompt skeleton's `00_prepare.py --audit` prints before any model call — items, mean words, the markers and confounds the area lists — doctrine too, and static evidence only: an aid for the judgement the Data profile field owes and for the audit, never proof that the data fit the question. Model calls are split between `llm` (aliases, retries and call records), `llm_specs` (one configuration type per backend, validated when loading `models.toml`) and `llm_backends` (the wire calls). `llm_cache` keeps a lab's raw model answers across runs (`cache/llm/` in the lab repo), keyed on the answering model, the answer-changing spec fields, the prompts and the sampling values; a run opens it in one of three modes — normal, replay (no model asked, a miss stops the run), repeat (never read) — and records the mode and every call, hits with their origin (`llm-cache.json`, `llm-calls.jsonl`). `endpoint_lease` manages the model-slot lease.

`runlog` calls `llm` to record resolved models. `endpoint_lease` checks liveness through `runs.is_alive`, without calling the run writer.

### 3 · Checks

`labkit/checks/` answers individual questions about code, recorded metrics or notes. `intent_check` compares promises with run records. `code_check` collects the code checks and writes the audit bundle; `code_scan` supplies the source facts those checks share, such as fields and stages; the keys of the materialized data come from `scope_sha.data_keys`. `gate_label_scan` extracts string comparisons, `import_check` identifies code the stamp cannot follow, and `prompt_check` checks parser fixtures and prompt drift, and refuses the start of a run whose templates are not registered verbatim (`require_registered_templates`, called by an area whose pipeline loads its templates from files).

`run_record_check` checks what a finished record must show: every source frozen, the bytes the run recorded and tracked or ignored by a rule, model identity (each line of the run's call log with a record naming its alias: the run's own, or that of the run that stored the answer), draws, row provenance and arms; `kept_number_check` the numbers it reports — a criterion's denominator against a recorded input count and the kept number as the head's `[kept]` names it. `origin_check` holds each input whose record names an origin run to that run's record and the file's bytes now (finalize's input-origins station, and the `INPUT ORIGINS` piece the analysis audit is shown). `readme_check` checks whether an area's README can lead a reader; `notes_check` checks measurement-note declarations. `audit_binding` answers what an analysis audit is held to: the answering run it reads (`audited_run`), what it was shown of that run (`run_shown`, the digest the record carries) and which records cover the area now (`covering_analysis`) — one answer for `labkit-audit`, report-check and `protocol-fill --from-run`. Among what it shows is the protocol each origin run of an input was measured under, as that run saw it when it started — its recorded commit with its `uncommitted.patch` (`source_protocol_pieces`, through `protocol_then.as_measured`), never the protocol as it reads now nor a newer run's; where that cannot be read back the piece says why and shows no other text, and finalize holds the run when the origin run was bound to a protocol (`source_protocol_finding`). `protocol_runs` shows every run of the protocol audited and of each protocol a source was measured under — completed or not, deleted, or known only to the run index — grouped by step, each with its state, result, registration then and code then as a diff from the compared run (`run_code.code_then`: commit plus `uncommitted.patch`), the whole diff as a `RUN DIFF` piece of its own while the audit's diff budget lasts, past it named not shown in full with an excerpt and the rest unread (`labkit-run-diff` prints it for a person). The auditor asks for such a diff, one path's section of it or lines of one file's side, with a finding's `check: diff:<run>..<run>[:<path>[:old|new:<from>-<to>]]`, and for a file as a run started from it with `check: code:<run>:<path>[:<from>-<to>]` (`required_check.evidence_request`); once a person decides that finding, every later audit shows it as a `REQUESTED DIFF` or `REQUESTED CODE` piece served first from the budget (`followup.diff_requests`, `protocol_runs.requested_pieces`), and the follow-up's verdict on an undetermined finding stays `not_assessable` while the piece is missing. A request a follow-up judged `resolved` or `unresolved` on the piece shown stands after that as a `judged:` piece (the verdict and the text's digest) and takes no room; the record that judged binds the state after its own verdicts (`audit_prompt.shown_after`). The pieces are in the bound digest, so a new run of such a protocol stales the audit. Finalize calls the run record and README checks as separate stations. `recheck` connects recorded outputs, recomputed metrics and the cited result.

### 4 · Gates

`labkit/gates/` sequences checks at decision points. The entry points `preflight_area`, `finalize_area` and report-check's `chain_gaps` show the stations and every condition under which a station is skipped. Station functions hold the detail and report through `gate.Findings`. `chain_gaps` lists the release stations in order — evidence, declaration, freeze or committed registration, finalize, full-run eligibility, analysis coverage and rendered results, recomputation, decision reviews, report — and returns what they found as data (`report_check.ReleaseChain`): `report_check` prints it, `next_step` reads it. The lane's conditions stand at those calls; a blocker does not stop later applicable stations. The nested finalize passes its blockers and warnings on, and a cause finalize already holds on the same text is not held a second time. finalize's comparison of the answering run with what its first measurement registered, and which change a correction in place releases, stands in `registration_hold`. Its Checked context (`report_context`) supplies this gate's declaration and answering run; the replacement station stands in `report_replacement`, the stations on the audit decisions in `report_decisions`. Nested finalize and the analysis script read their own inputs.

`agent_hooks` calls the gates during an agent session — the stop and the commit itself, the pre-run and post-change hooks in `hook_pre_run` and `hook_post_change`, what a hook knows of its session (the session log, the stop's base, the session's commits) in `hook_session`; `claude_hooks` and `codex_hooks` adapt each harness to those shared checks. `undecided` answers what the stop and the commit hold of an area's audit evidence beside report-check — an undecided audit BLOCKER, a record or journal lost, evidence changed — and `next_step` names its step. `audit` runs the agent review through `llm` (`audit_call`: the call as a journaled attempt, the token room and the refused errors, shared with both reviewers): `audit_prompt` builds what the auditor is shown and binds it to the stamp, `audit_reply` reads its answer, and `audit_decisions` lists and stores the person's decisions (`--findings`, `--decide`); `decision_review` runs the second auditor on the `stands` decisions of one record (`labkit-audit --review`); `report_review` runs a cold reader on a report — owed by one that discusses a run and by the one a head registers (`labkit-audit --report-review`) and records its claims (`formats/report_reviews`), which report-check holds the report to; `claim_review` stores the person's decision on such a claim (`--report-review REPORT --decide`, `false-positive` only) and runs the second reviewer that confirms it (`--review --record <report review>`). `install_hooks` installs the git hooks that run the gates; preflight checks that they are installed.

**The file rule.** A gate or check opens no file: it reads the area through the state (`area_state.state_of`) and the audit evidence (`evidence.read_evidence`), both built by the entry — the context (`report_context.checked`), a command's main, a hook — in the file state the entry judges (the index at the commit, the tree at the stop and the console) and handed down; a station builds none; a hold over several paths keeps them in `report_hold.Sources` (`held_state`, `held_evidence`) for every protocol and report it touches, and the builds are counted by test (`OneStateBuildPerCheckRun`, `TheFileStateNamedIsTheOneRead`) and the formats' readers (`runs`, `repo`, `scope_sha`, `evidence`, `jsonl`), and holds what they return. `tests/test_architecture.py` holds that (`NoFileAccessInGates`) with the exceptions named by their nature: the hooks and the installer, which read the harness's event, the session log and the hook files; the audit commands, which read the prompt's pieces and write records; the notes command; and the functions that run a program or check a command-line argument before any state exists (`preflight.area_tests`, `report_check.check_analysis_script`, the argument readers of `code-check` and `intent-check`). The list is not extended in passing.

### Tools

`labkit/tools/` provides commands that may use any layer. `protocol_fill` fills protocol fields and adopts a run: its text edits stand in `protocol_edit`, the writers of the result section in `protocol_result`. `scaffold` stamps a lab repo and its areas from the shipped templates; `protocol_cuts` cuts the protocol template to the items a form carries (`form_cut`), which `protocol_check.in_form` decides. The estimator script fits models only for `kind = "fit"`; a local `apply` uses the unchanged predictor, its null lane on labels permuted with the seed (or a registered fixed null predictor). Declared predictor artifacts are run inputs, hashed in the config and output fingerprint so resume and repeats cannot silently change them. `repo_check`, behind `labkit-check`, compares the installation with the repo's pin, checks whether that pin is current, and compares the repo's `AGENTS.md` with the one the installation stamps (`repo_check.agents_text`, which `scaffold` stamps with). `params` displays a run's values and provenance; `calltree` shows what a command actually called. `check_inventory` lists every place the code tells a finding, with the rule it cites and the commands that reach it, and every active rule with the places that cite it; with `--records` also a lab repo's audit findings per rule and its `new class` findings for review — the basis for measuring whether a rule earns its place; checks have no switches ([note](notes/2026-11-09-checks-have-no-switches.md)). Its call graph follows a method called on an object where annotations tell the object's class (`method_receivers`: a parameter, a return value, a dataclass field); a method called on any other object is not followed. `test_inventory` runs labkit's own suite once with every gate finding and every `SystemExit` raised in the package with a string message traced and tells, per rule and per finding site, which tests reach it, in which test files, how many of them carry the mark `rule`, and through which layer — a whole command, or a gate, check or format function — the basis for the test model; printed lines are not traced. `gate_stations` writes `docs/gate-stations.md` from the same scan and the gates' numbered station comments: per station the functions it calls, the finding sites they can tell and the way out each names (`FindingSite.way_out`), the sites a call reaches further down as a static estimate. `check_overview` writes `docs/checks-overview.md` from the scan of `check_inventory` and the reach a traced run left in `docs/checks-reach.tsv` (`test_inventory --reach`), each site named by its function, channel and message text instead of a line.

## Run records

An experiment script enters `runlog.run(...)` with its protocol, config and input paths. Preparation resolves the binding and records the promise snapshot; the start checks refuse an inadmissible run before its directory is created. The context manager confirms completion only on a clean exit. An interrupted run leaves its start record without confirmed completion.

```text
experiments/NN-name/
  PROTOCOL-name.md
  scripts/                      measurement and recomputation
  output/                       registered output files
  audits/                       findings and their decisions
  runs/<run-id>/
    config.json                 start config, protocol binding, inputs, environment
    metrics.json                values reported through run.metrics(...)
    outputs.json                registered output paths and their digests
    completion.json             confirmed completion and end state
    script-source.py            snapshot of the script as it ran
    code.json                   the code it imported, per git repository; code/ holds patches and copies
    start-file                  the start mark: a start file was written for this run (its path) — evidence of the start-file duty
  run-starts/<run_id>.json      the run's start file: run id, protocol id, UTC start, run kind — tracked, written once at the start
  runs.tsv                      derived index of completed runs — git-ignored, `runlog reindex` rebuilds it
```

The record can also hold raw model output, a patch and untracked source snapshots. Consumers read records through `runs`; `answering_run` selects the completed run bound to the protocol. The run index and the protocol run list do not choose the answer. Selection and run relationships are specified in [protocol-run-binding](protocol-run-binding.md).

## Where verdicts are recorded

Audits, reviews, runs and sessions leave records; the mechanical gates leave stdout and an exit code — by design, written down here (audit 2026-10-23). ## Run and hook enforcement

The Claude Code hooks load only in a session started in the repository root: Claude Code reads a project's hooks from `.claude/` of the directory it starts in, with no fallback to a parent; `labkit-hooks install` says so, and the git pre-commit holds a commit wherever the session started.

`standard_contract.lane` supplies the obligations for a protocol's cost tier. At `low` there is no freeze or preflight audit; release of a result still requires a full run, a clean finalize, a decided analysis audit bound to the current code, promises and answering run, and the recomputation check. At `high`, the start of a full run also requires a frozen protocol and matching preflight audit coverage.

The audit field is checked against an actual record under `audits/`. Changing the bound code or promises invalidates that coverage. An analysis record additionally names the answering run. Snapshot binding and the declared-scope hash have separate purposes; see [promise-block](promise-block.md) and [the chain](chain.md).

`run_kind="measurement"` declares a measurement; `run_kind="probe"` declares an instrument check. `run_kind="preparation"` records data preparation without releasing a result. At low repeat cost a separate probe is refused: the complete measurement checks the instrument and can be repeated cheaply. `runs.unreportable` refuses a probe or an acknowledged unfrozen run as the source of a reported number. At high repeat cost, `LABKIT_UNFROZEN=1` permits an acknowledged run only when a matching failed preflight attempt is recorded with sufficient timeout. The run records that attempt and the acknowledgement; the resulting number remains unreportable. An open audit BLOCKER cannot be overridden this way.

Adoption through `protocol-fill --from-run` writes Recorded results and Runs lines (the Summary's Conclusion stays the author's sentence), runs `report-check` against the written protocol and restores the file on failure. `[result] run` in the head declares a reported result; the hooks recheck affected areas so later edits are subject to the same contract. An exploration declares no result and releases none.

`labkit-hooks install` installs the pinned package's git, Claude and Codex hooks; `preflight` checks their installation. The run writer and git hooks work without an agent harness. Codex hooks need project trust and review via `/hooks`; installation checks inspect files, not runtime trust. [Codex hooks](codex-hooks.md) defines the adapter and its limits. Live hook configuration is generated by `gates/install_hooks.py`; it is not a second hand-maintained configuration in the README.

### Long-running commands

A harness that kills foreground commands can interrupt an experiment. Set `LABKIT_FOREGROUND_TIMEOUT_S` in that harness's environment policy so every command inherits it; `0` means no limit. Claude Code supplies a 600-second default through `CLAUDECODE` when no explicit value is set. An export inside a single tool command does not configure later commands.

When the lane requires background execution and a foreground limit is configured, `runlog` refuses a full run and asks for `runlog start AREA -- COMMAND`. The command starts a separate session and writes a log under the area's `output/`; `runlog AREA --wait` monitors its recorded state. A caller that already detached the process can declare `LABKIT_DETACHED=1`. The low lane allows foreground execution.

An audit's duration is separate from a measurement's repeat cost. Use the harness's background-task mechanism for a long `labkit-audit` call and wait for that task, rather than polling process-name matches.
