# Exploratory workflow: one investigation, each run bound to its own intent

> Workflow direction approved by the author on 2026-11-14; the investigation boundary was agreed on 2026-11-16. This is the contract and implementation plan, not an implemented feature. Current standard 0.31 still applies. [TODO](../../TODO.md) holds the work order. No experiment, release or rollout follows from this plan. Step 1 (record design) is worked through against the code at `89815c4f` in [Record design worked through](#record-design-worked-through-2026-11-16). The author answered two drafts on 2026-11-16 and kept the architecture; the remaining format decisions and names await the author. The first build step, inputs and origins, is built in part (`9c694796`): see [Implementation status](#implementation-status).

One exploratory protocol may contain several related questions and measurements. The investigation develops as results are seen; each run retains the question, procedure, inputs, settings and assessment that it actually investigated. A new protocol is needed for an independent investigation or a separate confirmation, not for every justified refinement within exploration.

## Current behaviour and why it changes

`type` identifies exploratory or confirmatory claims, but `standard_contract.lane` selects obligations by repeat cost and `registration_fields` selects them by experiment kind and whether a model is named. The guide explicitly retains criteria and audits for exploratory fit and apply experiments (`labkit/docs/agent-guide.md`, “Choose the experiment”). `registration_hold.registration_changes` binds later measurements to the first measurement's promises; `scope_changes` also holds changes to what the number is about. These checks have no exploratory exception.

Today, a changed scientific choice usually requires another protocol. Existing successor checks and predecessor evidence protect against making an earlier miss disappear through a changed question. The exploratory workflow must preserve that evidence while allowing related changes within one protocol. It must also preserve the scientific distinction between exploration and a confirming evaluation whose relevant choices preceded the results.

## Agreed workflow contract

| Concern                | Exploratory workflow to implement                                                                 | Confirmatory workflow                                                    |
|------------------------|---------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| Unit of work           | One developing investigation, potentially several related questions and runs                      | A separately registered confirming investigation                         |
| Question and procedure | May change between runs, with the change and reason recorded                                      | Relevant choices fixed before the evaluated results                      |
| Success criteria       | Optional unless the task requires an assessment; additions and changes are explicit               | Registered before the relevant measurement where a criterion is required |
| Run evidence           | Each run retains its own intent, code, inputs, settings and results                               | Same provenance, plus the fixed registration                             |
| Selection              | Seeds, variants and runs may be compared; explain selection and its basis                         | Follow the registered selection and analysis plan                        |
| Audit                  | Judge measurement validity, the question actually investigated and the support for the conclusion | Same duties, plus adherence to registration                              |
| Report                 | Identify source runs, relevant changes and decisions made after observation                       | Report the registered comparison and justified deviations                |

The author confirmed on 2026-11-16 that related questions may remain in the same exploratory protocol. The boundary is scientific continuity: refining a question or investigating an observed failure does not by itself require a new protocol. An unrelated investigation or a move to confirmation does. The audit judges that continuity from the stated reason and evidence; text equality cannot establish it.

### What may change

After inspecting a result, the agent may revise the question, method, seed, data selection, filter, analysis or assessment for a subsequent exploratory run. It records what changed and why, including when the reason came from earlier results. This is permitted exploration, not a false claim that the change preceded observation. Explicit task requirements remain owed: a task's requested comparison or answer cannot be dropped by labelling the work exploratory.

A success criterion is not required solely to make an exploratory fit or apply produce a pass/fail verdict. The measurement must still be sufficiently specified to interpret its outputs, and task-required assessments and relevant measurement-validity checks remain. Experiment kind continues to describe what a number asserts: tuning a predictor cannot silently remain an unchanged-predictor application. How such changes are represented is a design question, not permission to mislabel a run.

### What remains bound

The current protocol may evolve; a completed run's evidence does not evolve with it. Its question, settings, data, measurement code, recorded criteria and results remain reconstructible. A later criterion cannot rewrite an earlier verdict. Reanalysis of retained outputs identifies the source measurement and the new analysis separately; it does not overwrite the original measurement.

Each run still needs a current intent when it starts. Recording what the next run does is not a claim that the whole exploration was planned before any results. Reuse the existing commit, patch, configuration and promise-snapshot machinery where sufficient. Before implementing an additional field or file, identify what those sources already retain and which reader needs any missing information. Missing evidence must be named, not reconstructed from memory.

Earlier auditor findings and second-review outcomes remain available. Changing the question alone does not resolve a code fault or erase a rejected decision. For each proposed result, the audit needs the applicable run intent and implementation, the changes relevant to its interpretation, and the selection or comparison on which its conclusion rests. A previous audit cannot silently cover changed inputs or claims.

### What is separate

Existing cost-based instrument and code checks remain owed; an expensive exploration is not an audit exemption. Approval of an instrument before a costly run must be distinguished from freezing a hypothesis for confirmation. The audit supplies evidence about semantic fit, not proof that an instrument measures the intended construct.

The global release policy approved on 2026-11-16 is a separate work item. Exploration alone does not authorize release despite an audit BLOCKER. Until that policy is implemented, the existing release rules apply. A later implementation must preserve the distinction between exploratory status and permission to release with a documented objection; readable evidence and available measurements remain technical prerequisites.

Confirmation starts a separate protocol that identifies the exploration it builds on. Relevant choices precede the confirming evaluation. Whether the confirming data were already evaluated for that question is judged by the audit; a new path or file is not sufficient evidence. Changing `type` on an existing protocol cannot retroactively turn selected exploratory evidence into confirmation or remove a historical confirmatory miss.

## Walkthrough to make executable during implementation

This is a design example, not a new research experiment. It deliberately requires a report that depends on more than one run.

| Step                       | Work within one exploratory protocol                                                                                                          | Retained evidence and expected behaviour                                                                                                                             |
|----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| A: inspect errors          | Ask which errors predictor X makes and measure its outputs. A success threshold is absent unless the task requires one.                       | Run A retains this question, the data, code, settings, predictions and scores.                                                                                       |
| B: investigate a filter    | Errors in A suggest a filter. Record that reason, implement the filter and measure again.                                                     | Run B retains the revised question and filter. No new protocol is required solely for that refinement; A remains as measured.                                        |
| C: compare                 | Compare retained cases, errors removed and cases lost between A and B. If the analysis changes, record its source runs and analysis code.     | The comparison cites both runs. It does not treat A as if it had used B's filter, or report only the improved score while hiding changed coverage.                   |
| Audit and report           | Audit the measurements and comparison supporting the selected conclusion. Explain why the filter was investigated and whether it is retained. | The auditor sees both relevant run states and selection context; the report identifies the conclusion as exploratory. Applicable findings and release duties remain. |
| Confirmation, if requested | Start a separate confirmatory protocol linked to this exploration.                                                                            | The relationship and prior selection reach the confirming auditor; the old exploratory result is not relabelled as confirmation.                                     |

The example requires no universal numerical definition of a related question. It does require a reason a reviewer can assess. A user may also end the exploration without a result; the existing handover duty must remain usable.

## Record design to settle before code

The first and largest design task is how one reported result can depend on several measurement runs. Compare two representations using the same A–B–comparison walkthrough:

1. **A selected result run with additional sources.** Retain a selected run as the entry point, but explicitly bind the other source runs and the comparison used by its conclusion. Determine where the comparison is stored and how its analysis is checked; a run list alone does not establish the comparison.
2. **A separately recorded analysis of several runs.** Represent the comparison as an analysis with identified source measurements, code and outputs. Decide whether this uses a run, an analysis file or a protocol block; do not assume a new experiment kind or command is needed before inspecting the existing machinery.

Several source runs need not mean several independently adopted results. Compare the concrete files, commands, readers and tests for both representations, then recommend the smallest complete first implementation. A first version may be smaller than the entire implementation sequence, but it must preserve each run's meaning and bind the current claim to its actual sources. It cannot consist solely of removing the exploratory registration lock while rendering an old result through the latest question. If the proposed first version postpones the agreed multi-run comparison, state that limitation and seek an explicit scope decision.

The remaining representation questions must be resolved alongside that choice; none is an additional approved field or command signature.

1. **Intent at each run and reasons for changes.** Inspect `protocol_history.as_measured`, which already reconstructs the protocol from commit and patch, together with run records and promise snapshots. Establish which needed facts are retained and where change reasons belong. Preserve current commit-before-run obligations unless a separate change is explicitly proposed.
2. **Changing kind and working mode.** Specify representation and allowed transitions when an exploration begins tuning a predictor or a confirming investigation becomes exploratory for future work. Historical run types and findings remain; a separate confirmation is never created by changing a label.
3. **Relevant audit coverage.** Decide which run and analysis inputs a proposed conclusion needs, how changes invalidate that coverage, and how follow-up findings are attached. Reuse existing formats where adequate; do not require a fresh model call for every descriptive edit merely for uniformity.
4. **Forms and instrument approval.** Define the minimum exploratory fields and template outputs without a success criterion. Inventory actual `frozen` consumers by purpose: instrument readiness, confirmatory prior commitment or another technical dependency. An occurrence count is not a change count. Identify the smallest central separation before proposing any rename or broad migration.

### Reader inventory required for both representations

A reader here means a function or command that consumes protocol or report information, including commands that select or write the reported result. The design must say which facts it takes from the run's retained state, which it takes from the current claim, and what relationship it checks. This is a list of intended responsibilities, not a claim that today's readers already implement them. Do not switch every reader wholesale to the historical protocol.

For example, A measured all cases and B later used a filter. A must remain an all-cases measurement. The current report may compare A and B, but must acknowledge the different case selection and support the comparison with both sources. Historical intent and current interpretation are both needed.

This is semantic judgement, not proof from text equality.                                     |
| Run finalization (`finalize`)                                                               | The run's intent, required outputs, measuring code and recorded inputs                          | The applicable current release context and any explicit repair/correction decision        | Validate the run against its own measuring contract; current edits must not silently replace that contract or erase an unresolved defect. Specify exact checks after inspecting its stations. |
| Promise validation (`intent-check`)                                                         | Promise definitions and expected keys for that run, paired with its actual outputs              | Any request to reuse the result under a changed assessment                                | Check recorded outputs against their own promises; a new assessment needs an explicit analysis rather than pretending it was the original criterion.                                          |

For each row and each representation, name the actual functions, files, command arguments and tests. Trace selection through `bound_answering_run` and `area_state` as well as direct calls, and inspect the affected command paths. The listed rows are the starting checklist, not a proof of completeness. An existing caller need not change if it already receives the right state; record that finding instead of scheduling a rewrite. Mark facts already retained, facts needing another reader, and facts genuinely missing. Distinguish exact technical comparisons from the auditor's interpretation. This is how implementation cost becomes comparable without guessing from module or occurrence counts.

These choices must be resolved before format-dependent implementation. They should not expand into a general study-management system, configurable rule engine or rewrite of every gate. A new warning for drifting questions is not part of this plan.

### Decided requirements this design must meet

These come from the author's decisions of 2026-11-14 and 2026-11-16 and are not reopened here.

1. One exploratory protocol may hold several related questions and runs.
2. Each run keeps the question, code, data and settings it was measured under.
3. Success criteria are optional in exploration unless the task asks for an assessment.
4. Measurement quality, provenance and the audit stay owed.
5. Confirmation needs a separate protocol.
6. The global release policy is a separate work item and is not touched here.

Two findings shape the design. First, per-run intent needs no new storage: `as_measured` already rebuilds it, but its messages say "its first measurement" (`protocol_history.py:729-764`) and need a neutral wording before other readers use it. Second, every reader except `registration_hold` reads the **live** protocol (`area_state.state_of`, `labkit/formats/area_state.py:357-367`; `labkit/tools/params.py:270`, `:327`). That is consistent today only because the registration lock refuses a changed protocol after the first measurement. Removing the lock alone would make `result_render` apply B's promise block to A's metrics (`labkit/checks/result_render.py:302-322`), `intent-check` report A's missing keys as defects (`labkit/checks/intent_check.py:257`, `:328`), `recheck` recompute A with today's `evaluate()` (`labkit/checks/recheck.py:356-382`) and `labkit-params` show B's constants as A's registration (`labkit/tools/params.py:127-167`).

Selection is one function for every reader: `Measured.told` → `bound_answering_run` (`labkit/formats/area_state.py:130`, `labkit/formats/answering_run.py:717`) returns the adopted `[result] run`, else the newest completed bound non-repeat run that reports an intent key. `report_context.checked` takes the same choice through `audit_binding.audited_run` (`labkit/gates/report_context.py:103`), so `labkit-next` and `report-check` inherit it. Every result format holds exactly one run: `RESULT_KEYS = ("run",)` (`labkit/formats/protocol_block.py:303`), the audit record's `run_id` and `shown_sha` (`labkit/formats/findings.py:1282`), the report block's opening line (`labkit/checks/report_blocks.py:100`).

### Exploratory per-run binding

First draft, revised in [Provenance between runs](#provenance-between-runs): the order of runs no longer comes from commits, and changes are declared against an explicitly named basis.

1. **Which runs are exploratory.** The workflow that applies is read from `type` in the first measurement's own text, not the live head. A `type` change after the first measurement is held in both directions with the way out "register a new protocol". Then relabelling cannot lift a confirmatory lock or turn exploration into confirmation. `type` is not among the parts `scope_differences` compares today (`SCOPE_FIELDS`, kind, `[kept]`, `[reference]`; `protocol_history.py:429-435`, `:478`); it would join them. *Decided by the author on 2026-11-16.*
2. **Lock replacement.** For an exploratory protocol, station 2 checks: every measurement's own text reads (`unread_measurements`); each run's declared changes match the differences against its declared basis; the live text equals the answering run's own text in the compared parts. A confirmatory protocol keeps today's lock unchanged.
3. **Kind changes.** A `kind` change between exploratory runs is a declared change. Each run keeps its own kind through its own text. A confirmatory protocol that should continue as exploration is registered anew; the existing `[replaces]` path carries it.

### Provenance between runs

Three relations, each recorded where it arises and none inferred from commit order:

| Relation                                            | Example                                                                 | Recorded                                                                                                                | Checked exactly                                                                                                                                                    | Judged by the auditor                                                                                        |
|-----------------------------------------------------|-------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| **Builds on**: what a run starts from and why       | B builds on A because A's errors suggested a filter; D also builds on A | The run's step in its own protocol text: basis run, the occasion and reason for the step, declared changes with reasons | The basis is a completed run of the protocol, not a repeat, present at start; declared changes equal the differences against the basis in the protocol parts below | Whether the occasion and reason justify the change; whether the question still belongs to this investigation |
| **Uses**: which files a run read                    | C reads A's and B's prediction files                                    | Each input of C's record: path, digest, and the run whose `outputs.json` holds that file with that digest               | One matching run: recorded; several: the script's explicit choice, checked against the file; a choice that does not match: start refused; no match: a plain input  | Whether C used the files correctly                                                                           |
| **Supports**: which runs carry a reported statement | The report's conclusion rests on C, and through C on A and B            | Adoption of C (`[result] run`), unchanged; the supporting runs are C's input origins                                    | Generated source lines in the result block; a changed source makes C's audit and block stale                                                                       | Whether the conclusion follows from C and its sources                                                        |

**The step.** A step is the intent of the next run or runs: one table in the protocol head, `[builds_on]`, with `id`, the basis `run`, `occasion`, `why` and its changes as `[[builds_on.change]]` in the `[[replaces.change]]` form (`what`, `from`, `to`, `why`; `labkit/formats/protocol_block.py:796`). Runs belong to the same step when their own texts carry the same protocol id and the same `[builds_on].id`; two protocols may both have a step `initial` without their runs being grouped. `occasion` is one of `observation`, `planned`, `repair`; the check is that the value is one of these, not that it is true, which the auditor judges. `why` is the one required reason of the step. A change's own `why` is optional and owed where the step's reason does not explain that change; no keyword check enforces it. There is only one current step. The history needs no list, because each run's own text (`as_measured`) holds the step that was current when it ran. Branching follows: B's text says "basis A, filter"; D's later text says "basis A, other variant"; E's says "basis B, new seed, no change". Several runs may share a step, for example seeds. A run id is written by a command, never typed: `protocol-fill PROTOCOL --builds-on RUN_ID --id ID --occasion OCCASION --why "…"` writes the table and the changes it computes against the basis's own text (`what`, `from`, `to`); it adds no `why` placeholder per change.

**Step decisions agreed on 2026-11-16.** One current step in the protocol is sufficient; each run retains that step through its own reconstructed protocol text. A new step states its starting point, occasion and reason. The occasion may be an observation, a planned variant or a technical repair; an empirical observation is not always required. Repetitions or seed variants within the same step need no repeated reason. No additional commit-before-every-run duty is introduced; the existing git and first-measurement obligations remain, and the protocol must be reconstructible from the run's retained evidence.

The basis of scientific development is distinct from `derived_from`, which denotes reanalysis of retained rows. For now the basis is stored only in the step table, not duplicated in a new run-record field. Consumers share the existing reconstruction rather than implement their own version. This decision does not remove the separately proposed origin fields for files read by C. If reconstruction fails, report that the basis is unknown and why. Hold only a validation or release that depends on that missing evidence; a display can show the unknown state. Do not invent the basis or block unrelated work solely because this reconstruction failed.

**Differences within the same step.** Calling a run a repetition does not establish that its method is unchanged. The auditor must be shown differences in code, protocol and relevant recorded settings among the reviewed runs of the same step, including uncommitted patches; comparing commit ids alone is insufficient. The design must identify the comparison basis and display distinct variants without requiring every pair of runs to be compared. An expected seed change and a changed filter may both be exact differences, but their scientific significance is judged by the auditor.

This is additional audit context, not a new scientific blocker or a rule that every code change creates a new step. Missing required fields of an explicitly declared step and the existing narrow declaration checks remain separate obligations. The code and patches already retain the differences; the missing feature is their explicit presentation in the same-step context. Showing a difference does not guarantee that the auditor interprets it correctly.

**Which differences are scientific decisions.** In the protocol: the parts the confirmatory lock already treats as what the number is about and as the registration — Question / hypothesis, Terms of this protocol, Data / scope, Exclusions / filters, Unit, `kind`, `[kept]`, `[reference]` (`SCOPE_FIELDS` and `scope_differences`, `labkit/formats/protocol_history.py:429-503`), and the promise block (`registration_differences`, `:530`). These are compared exactly against the basis's own text. The `[builds_on]` table itself and report fields are not compared. Outside the protocol: measuring code (`script_sha`, `code.json`), settings in `config`, input digests and resolved models. A refactoring cannot be told from a method change by an exact rule, so these differences are listed for the auditor and hold nothing.

**Declared changes: what the hold means.** An undeclared difference in the protocol parts, or a declared change the texts do not show, holds finalize and report-check, as `[[replaces.change]]` does today (`labkit/gates/report_replacement.py:137-208`); accepted by the author with this narrow meaning. The hold is a guaranteed check of one statement: every difference between the run's own text and its basis's own text in the listed protocol fields is declared, and nothing else is. It does not show that every scientifically relevant change was declared: a filter or a method can change in code alone, and then no protocol field differs. Its message and the docs say so, and the auditor still receives the code, settings and data differences against the basis and judges whether an undeclared method change lies among them.

**A run without a step.** After the first measurement, a run without `[builds_on]` must equal the first measurements in the protocol parts; otherwise it is held with the way out "declare its step". Protocols with runs under standard 0.31 are not read by the new version at all (see [What the format break affects](#what-the-format-break-affects)).

**Origins of input files.** Decided by the author on 2026-11-16: the first version resolves verified input origins only among completed runs of the same area. A and B stay in its measurement protocol; C is in its separate exploratory computation protocol in that same area. This is the scope of the uses relation, not a requirement that every related protocol in the repository share an area.

Ordinary input data may still come from elsewhere. A copied file or an input without a resolved origin does not acquire verified run provenance. An explicitly selected origin outside the area is refused (rule 3). A missing origin is shown, not held: the source station states it, and the analysis audit of C lists every input without origin, so the auditor judges any provenance claim the conclusion makes about it. No release is promised for such a claim, and no new hold is introduced. This does not claim to detect every copied external result automatically.

At start, runlog looks up each `data=` input among the completed runs of the area. Both digests already exist in the same 16-hex form (`labkit/run/provenance.py:457`, `labkit/run/runlog.py:626`). A digest proves equal content, not a unique origin: a deterministic rerun, a copied file or a resumed output can legitimately give several runs the same file. The rule:

A run is eligible as an origin when it is a completed run of the area whose `outputs.json` holds that path with that digest. The same eligibility applies to the lookup and to an explicit choice. A repeat (`repeat_of`) is eligible: being an origin says where a file came from, not that the run may be adopted or reported, which stays with the existing adoption rules (`runs.unreportable`). A repeat origin carries its `repeat_of` into the auditor's evidence.

1. Exactly one eligible run: its id is recorded in the input's entry.
2. Several: the start is refused unless the script chose the origin for that input explicitly. The refusal lists the eligible runs and the form of the choice.
3. An explicit choice is always allowed, also where the lookup finds one run, so a script can state from the start which run it means. The chosen run must be eligible; otherwise the start is refused. The choice is recorded the same way, with a mark that it was chosen.
4. No eligible run and nothing chosen: a plain input without origin. An analysis run whose inputs all lack an origin has no sources; the source station says so, and the analysis audit's evidence lists those inputs.

The recorded origin is final: a later run that writes the same file does not reopen it.

**Form of the explicit choice.** Decided by the author on 2026-11-16 (F14): a typed value in the existing `data=` entry that holds the file and the chosen run; `runlog.run`'s signature and the `data=` argument stay. This adds one public name. A run id the script names is checked against the file and the record, so a typing error cannot bind a wrong origin. `data=` already takes one typed value, `BinaryInput`, which `describe_data` unwraps (`labkit/run/provenance.py:419-460`): it records bytes only, while a plain path is read as text, counted and checked for row-id overlap across splits. The origin value is unwrapped in that same function, before any of these checks, and combines with `BinaryInput` instead of replacing it: naming an origin neither turns a text input into a binary one nor skips the text, row and leakage checks. The value is `runlog.RunOutput(path, run=RUN_ID)`, for a binary input `runlog.RunOutput(provenance.BinaryInput(path), run=RUN_ID)`: `RunOutput` states the origin, `BinaryInput` alone the handling of the file, so "binary" has one spelling. `describe_data` unwraps `RunOutput` first and passes the inner value to the existing handling. `RunOutput(RunOutput(…))` and `BinaryInput(RunOutput(…))` are refused with a sentence naming the input key. The input's entry in `config.json` gains `origin_run` (the run id) and, for an explicit choice, `origin_chosen = true`, which means chosen by the script, not confirmed by the auditor: a checked origin and a scientifically sound use of the file remain separate statements. `derived_from` is not reused: it has one parent, means "re-reads its rows, no model call", and its lineage walk compares the parent's code with today's code (`labkit/checks/run_record_check.py:112`, `labkit/formats/runs.py:1267`).

### Final form of the measurement protocol

A measurement protocol that registered a report, and whose runs are sources of an adopted analysis, closes with a generated block (F9). Written by `protocol-fill PROTOCOL --reported-through`, it states: "Reported through <computation protocol>, run <C>" — the protocol id and run ids of the sources, the computation protocol and run C, and C's adoption. Exact checks: C is adopted in its protocol, and each named run is an origin of one of C's inputs; the block is regenerated when either changes. The block does not:

- render a verdict or a recorded results line of its own: no passed measurement result is shown, and C's block carries the numbers;
- decide, close or hide a finding: the measurement protocol's open findings, limitations and handover duties stay where they are and keep their effect on stop and commit;
- replace the report review: the review owed for the report's final text applies to this block as to any other.

### Reported comparisons and their evidence (decided 2026-11-16)

The report combines compact generated source references and values from the recorded analysis C with an explanation written by the agent. The explanation must disclose selection decisions and changes material to the conclusion, rather than reproduce every technical change. It refers to the reasons retained when the relevant source runs started; it must not silently replace them with a retrospective account. Later understanding may be explained as later understanding. The report reviewer judges adequacy; no keyword check decides scientific transparency.

The planned step table is the protocol section containing the next run's basis, occasion, reason and declared changes, as defined in “Provenance between runs”. It is not an implemented feature. Its historical state comes from commit plus the run's uncommitted patch, not necessarily from a separate commit immediately before that run. Reasons stay in that retained protocol state; no additional reason field is added to the run record.

The reviewer must actually receive the relevant retained reasons and differences in protocol, code, data and settings, including within-step variants and patches. Merely storing them somewhere is insufficient. The agent's short report explanation is not the reviewer's only source. This evidence is limited to what was recorded; it cannot reveal unrecorded trials, and a seed difference alone does not prove outcome-based selection. Presentation of evidence does not guarantee correct auditor judgement.

Comparison quantities are computed by C's analysis script from its identified inputs and retained as C's outputs, then checked through the existing provenance and recalculation duties. Package gates do not perform a generic scientific comparison. When a filter comparison claims retained cases, excluded cases or errors removed, its source measurements must provide compatible case identities and the individual results needed to calculate those quantities. Other comparisons may need different evidence. This is not a universal requirement to retain every individual prediction for every exploratory run.

Missing evidence constrains the claim, not merely its wording:

- If a required historical reason or source state cannot be reconstructed, name the missing evidence and hold the dependent review or release. A present-day explanation cannot replace it. Unrelated work is not held solely for that failure.
- If only aggregate scores exist, they may support an appropriate score comparison, but do not establish which cases were excluded or which errors disappeared. C must not fabricate those quantities, and the report must not assert them.
- A narrower supported statement may be reported when permitted by the task. An explicitly required comparison that cannot be supported remains unresolved, rather than being silently reworded away. Any remaining scientific question is judged under the audit and applicable release rules.

This decides the report-content question: source lines stay compact, while the agent's explanation carries material selection reasons and the reviewer receives the relevant recorded evidence. It adds no new automatic significance claim and changes no implementation in this planning step.

### Findings of a source and their effect on C

Revised after the author's answer: a source finding acts on C by what it touches, not by its status. `fixed` first means "repair claimed".

1. **An undecided BLOCKER of a source** already holds every stop and commit of the area (`labkit/gates/undecided.py:40`); C cannot pass meanwhile. Nothing new.
2. **What C used is exact.** C's record names, per input, the source run and the digest of the file. When a source is re-measured after a repair, C still names the old run and its old files; the source station states, as data, that a newer run with a step basing it on the source exists. No status alone holds C.
3. **Relevance is judged.** Every source finding with a decision (`fixed`, `limitation`, `false-positive`, also an accepted WARNING) is shown to C's auditor with its decision, its reason and what the record says the repair changed (a corrected protocol field, `findings.corrected_field`, or measuring code). The auditor answers per finding: it touches the data C used, it touches one or more of C's conclusions (named), or it touches neither. The reply must cover every shown finding, which is checked exactly; the classification is the auditor's.
4. **What follows from the answer.** Touching the data C used is a finding on C: a repaired computation fault needs new source values, so C is computed again on the repaired run. Touching a conclusion is a finding on C decided under the existing rules, including a limitation whose effect names C's promises (standard 0.31). A corrected description that touches neither leaves C as it is. The global release policy is not involved.

The audit sees, per source: its own text, its step and declared changes with reasons, its metrics and rows, and its code at its commit. The last one needs a reader over `repo.blobs_then`; it is not shown today.

### Link from a confirmation to its exploration

Revised after the author's answer: the confirmation names an explicit state of the exploration, and only a change of that state makes its review stale.

**Scope of the link.** Decided by the author on 2026-11-16: the later confirmatory protocol may be in another area of the same repository. It explicitly references the named exploratory state; this relationship identifies the basis of confirmation and does not transfer measurement values or extend C's input-origin search to other areas. Validate the repository-wide protocol identity and the bound run and source state, rather than require the same area. Cross-repository confirmation links are outside this first-version scope.

**The link.** A confirmatory protocol names in its head, in the table `[explored_in]` (`protocol`, `run`; not `[replaces]`, which means an invalid registration replaced), the exploratory computation protocol and the analysis run it builds on. Both references are needed: a run id is unique only within its area (`labkit/run/runlog.py:345`), so the protocol id locates the area, and the run's `config.json` names its protocol, which makes the pair checkable. Decided by the author on 2026-11-16 (F12): the named run must be the adopted run of that protocol — any completed run is not enough, since the confirmation examines the exploration's own selection. This is a contract condition, not only an input check of the command. `protocol-fill CONFIRM --explored-in EXPLORATION_PROTOCOL` writes the two references: it reads the exploration's adopted run once and stores both ids, and no later check re-selects a newer adoption. Basis, selection and conclusion below are derived from them and are not separately maintained fields. Validity is checked by that command and again at the start of the first confirming measurement. The check does not attribute authorship or reject a table merely because it was edited by hand. It refuses an invalid protocol/run association, a run that is not adopted or a withdrawn adoption. It adds no audit condition: existing audit duties and the staleness rule below apply unchanged. The exact reference conditions are: exactly one protocol of the repo has that id; its first measurement was exploratory; the named run is a completed run of it and its adopted run. After the first measurement the link is compared like any registration part, and a change of the bound state follows the staleness rule below.

**The named state and its binding.** The confirming audit binds three things, and only these:

| Part       | What is bound                                                                                                             | Changes that make the review stale                   |
|------------|---------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------|
| Basis      | The named run's record and outputs, its inputs' origin runs and, through their steps, their bases, each with its own text | A changed record, output or own text in that closure |
| Selection  | The exploration's adoption (`[result] run` of the computation protocol)                                                   | Another run adopted, or the adoption withdrawn       |
| Conclusion | The Conclusion of the computation protocol as it stood at the audit                                                       | A changed Conclusion                                 |

A later exploratory run outside this closure — an independent side run — does not make the review stale. Today `predecessor_evidence` binds every run record of the predecessor (`labkit/gates/audit_prompt.py:362`, `scope_sha.predecessor_basis`); for this link the binding is narrowed to the closure above.

**Further data use.** Decided by the author on 2026-11-16: only a change of the explicitly bound basis, selection or conclusion requires a new review. Other data use that could question the independence of the confirming investigation is put before the auditor; it does not by itself make the review stale. Equal digests are one hint of such use, not a complete proof: they catch identical files only, while a subset, a re-encoded file or the same items under another name need the auditor's judgement. A later exploratory run whose input digest equals an input the confirmation recorded is therefore static evidence: shown at every confirming audit, and after an audit reported by report-check as a warning that names the run and the way to have it reviewed — never a blocker.

**What the confirming auditor sees.** The existing evidence (registration and inputs of every run of both protocols) extended with the closure's own texts, steps and changes, the adopted analysis and its Conclusion, and any further data use found by digest. Whether the confirming data were already evaluated stays the auditor's judgement. A confirmation without the link is not detectable mechanically; the agent guide asks for it.

#### What the format break affects

Revised after the author's objection that "old records stay readable" proves no compatibility. The question is which version must understand and check the origins, and that no version may silently ignore them. Two exact version checks exist today and decide it:

- **Protocol head:** a labkit reads exactly one standard; any other value is refused, older or newer, and "a protocol with runs is reproduced with the labkit release it was written for … never converted" (`labkit/formats/protocol_block.py:947-957`).
- **Run record:** a labkit reads exactly one `schema_version` (`runs._schema_problem`, `labkit/formats/runs.py:712-732`, `RUN_SCHEMA = 4` at `:81`); the precedent is 0.104.0, which raised it from 3 to 4.

The input entry parser alone would ignore an unknown key (`labkit/formats/runs.py:428-454`). That is why the origin must not rely on it. Decided by the author on 2026-11-16 (F13): the new runlog writes `schema_version = 5`, and the new labkit reads exactly 5; no record is converted. `_schema_problem` gains a sentence for schema 4 naming the last release that writes it — the release immediately before the one that introduces schema 5 (0.113.0 as of 2026-11-16; set when the break is released, and checked by a test against the tags like the existing sentences for schemas 2 and 3).

`RUN_SCHEMA` also stamps `code.json`, the record of the code a run imported (`labkit/run/code_repos.py:245`), so that file moves to 5 with `config.json`. A search on 2026-11-16 found no reader of `code.json` in the package, only its writer; the reader inventory before the break names it explicitly, together with every reader of `config.json`, and the rule test of each refusal covers both files. Then:

| Reader                                 | Meets                                                                                                                                           | Result                                                                                                                                                     |
|----------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|
| New labkit                             | New protocol and schema-5 record                                                                                                                | Understands and checks the origins; the only version that does                                                                                             |
| Older labkit (standard 0.31, schema 4) | New protocol                                                                                                                                    | Refuses the head before reading any run: no gate runs, so no origin is ignored                                                                             |
| Older labkit                           | Schema-5 record, also through a tool that reads runs without a protocol (`runlog` listing and `--wait`, `runlog reindex`, the usability scorer) | Parses no field: `parse_run_config` checks the schema first (`labkit/formats/runs.py:1127-1131`); the run is shown as unreadable with the version sentence |
| New labkit                             | Old protocol with runs                                                                                                                          | Refused by the standard check as today; reproduced with its commit and its pinned release                                                                  |
| New labkit                             | Schema-4 record                                                                                                                                 | Refused by its schema version; such a record belongs to a protocol with runs under an older standard, which is already history                             |

| Record or workflow                               | Effect                                                                                                                                                                                                                                  |
|--------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Protocols not yet run                            | One-line migration: set the new standard version                                                                                                                                                                                        |
| Protocols with runs, exploratory or confirmatory | Not converted: reproduced with their commit and pinned release; further work in a fresh area. This follows from the standard check alone; the schema version adds no further break for them                                             |

| Run records written after the release            | Schema 5, origins included; refused by every older labkit                                                                                                                                                                               |
| Confirmatory protocols started after the release | Behaviour as today, except that a `type` change after the first measurement is held                                                                                                                                                     |
| Reports                                          | Result blocks of areas at the new standard: source lines only for an analysis run with origins; reports of history areas are checked with their release                                                                                 |
| Public API                                       | One added name for the explicit origin choice (F14); `runlog.run`'s signature unchanged                                                                                                                                                 |

Whether an unknown head table is refused by an older labkit no longer matters: the standard check refuses the head first.

**Limits.** The digest proves that C read files identical to the sources' outputs, not that C used them correctly. The fairness of a comparison across different case selections, the relatedness of the questions, the sufficiency of a reason and the relevance of a source finding remain audit judgements. `as_measured` cannot read a run whose commit is gone or whose protocol was untracked; such a source holds instead of being reconstructed. Code, settings and data differences between a run and its basis are shown, never checked for a declaration.

**What removing the lock alone would break.** Without items 3–6, B's block would render A's verdicts, `intent-check` would call A's missing new keys defects, `recheck` would recompute A with B's code, and the comparison would have no checked home. That is why the lock split is item 1 of eight, not the whole change.

- Tests: `tests/test_input_origins.py` (rules from data in memory, file checks with and without origin, real runs through `runlog.run`), one contract test in `tests/test_public_api.py`.

Deliberately not built, and why:

- **No origin is written.** The decided origins are held on the `Run` object only. Under run schema 4 an older labkit would read a record with `origin_run` and silently ignore the key ([What the format break affects](#what-the-format-break-affects)); the fields appear together with `schema_version = 5`.
- **One new start refusal under the old schema.** Several eligible runs without a choice (rule 2); it does not depend on persistence. Recorded as Breaking in `CHANGELOG.md`.
- **A run whose record does not read is not eligible.** Its `config.json`, or as a completed run its `outputs.json`, does not read: a choice naming it is refused with the reason, any other start is not held. A first version refused every start with inputs in such an area; the commit hook showed it pre-empting the narrower refusals of `repeat_of` and `derived_from` (`tests/test_repeats.py`), and the damage is already held where the run is read for what it is. Open for the format step: whether the record notes that the lookup passed over an unreadable run, since such a run may have written the file.

What the format step needs next: `RUN_SCHEMA = 5` for `config.json`, `completion.json` and `code.json`; `origin_run` and, for a choice, `origin_chosen = true` in each input's entry, written from `Run._input_origins`; the data entry parser (`runs.data_entries`) reading and checking both keys; the schema-4 sentence in `runs._schema_problem` naming the last release that writes schema 4, with its tag test; every reader of `config.json` and `code.json` inventoried; acceptance cases 20 and the recorded part of 31 and 33. ## Acceptance scenarios and limits

Use pure tests for conditions, gate tests for selection and wiring, and scenarios with real commands for state passed between commands. Before claiming the new behaviour, show the old exploratory refusal and retain the corresponding confirmatory countercase.

1. Run the A–B–comparison walkthrough within one exploratory protocol. The audit and report identify both source states.
2. Compare several seeds; retain settings and the reason for selection without an automatic significance claim.
3. Change a question, filter or criterion between exploratory runs; old runs retain their original intent and verdicts.
4. Reanalyse existing outputs; keep measurement and analysis provenance distinct.
5. Attempt a prohibited registration change in a confirmatory protocol; it remains blocked.
6. Repair faulty measurement code; the next run is separate evidence and required audit/follow-up duties remain.
7. Select an older run while the live question is newer; no silent reinterpretation or stale audit release is allowed.
8. Change a protocol's type after a confirmatory miss or rejected decision; history and unresolved findings remain.
9. Verify that a criterion-free exploration still reports requested task assessments and measurement defects.
10. Start a separate confirmation linked to exploration; the auditor receives the exploratory basis and the claimed grounds for confirmation.

Run touched tests during implementation and the configured commit checks, followed by the full suite at integration. Review the final change independently and follow printed repair paths in a freshly stamped lab with supplied auditor answers. Those checks establish technical behaviour, not the judgement quality of real auditor models. A usability experiment and rollout to other repositories each require a separate instruction.
