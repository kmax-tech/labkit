# Which rule each finding holds — proposal for 2026-11-09

*Proposal · for the author to decide row by row; every row was read at the code (review and code check below), nothing in it is approved and the decision column stays open · sites as at 60f1c576 (unchanged since ffde5838)*

Of the 201 finding sites that cite no rule (`python -m labkit.tools.check_inventory`: 228 finding sites, 27 of them cite a rule), 147 are sites that can report a possible violation of a rule — an inventory of the code, not a count of violations found in use. 42 report that a check stays open, each naming the rule of that check, counted apart: 8 because the check cannot be executed, 10 because a required input is missing or malformed — a determined defect, held by a rule where its text requires the input and otherwise by labkit's technical contract —, 24 where one handler catches both and the site cannot tell which. 12 hold no rule. With the possible-violation rows taken, 29 of the 97 active rules are assigned to at least one finding site (today 11 cited by one). An assignment says which rule a site reports on, not that the rule is enforced in full.

## Limits

- "No finding would hold it" is about finding sites. A rule can still be held without one: by a helper's design (`LAB-064 The pilot is resumable too` — `batch.Store` resumes), or by a `console.Refused`, which the inventory leaves out as "the command cannot run".
- `LAB-069 No LLM cache` said the lab keeps no cache while labkit shipped one (`labkit/run/llm_cache.py`). Settled in standard 0.27: LAB-069 No LLM cache unless the lab declares one; the cache opens where `models.toml` says `[llm_cache] enabled = true`.
- Every row was read at the code (the call and the lines around it), not every function it calls; "sure" means the rule's text names the hold.
- The inventory sees a rule only in the strings of the call. `labkit/checks/import_check.py:113` cites LAB-019 The stamp covers everything that determines the number through an argument its caller passes, so it counts as citing none.

## How to read it

| Class                | Meaning                                                                                                                                  | Rule column                                                |
|----------------------|------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------|
| possible violation   | the site reports, when it fires, that a rule is broken                                                                                   | the rule it would report                                   |
| check not executable | the check cannot be executed on a possibly correct input: a limit of the check, git, a permission, pytest                                | the check left open                                        |
| input defect         | a required input is missing or malformed: a determined defect, and the check it feeds stays open                                         | the check left open; the duty broken in "Checks left open" |
| mixed handler        | one handler catches a missing file, an access error and an invalid format alike; which happened is not told                              | the check left open                                        |
| contract             | a technical contract of labkit, documented, not a rule of the standard: the protocol id that binds runs (`docs/protocol-run-binding.md`) | —                                                          |
| rule candidate       | a condition the code holds that no rule names, kept open until a rule has its own use and grounds                                        | —                                                          |
| pass-through         | the message is built elsewhere; the rule belongs where it is built (none left after tracing)                                             | —                                                          |
| mechanical           | a precondition of the check itself (index against tree, an adoption cut off, a symbolic link)                                            | —                                                          |
| usage                | a wrong command line                                                                                                                     | —                                                          |
| not-lab              | a developer probe, no lab check                                                                                                          | —                                                          |

| Confidence | Meaning                                                        |
|------------|----------------------------------------------------------------|
| sure       | the rule's text names what the check holds                     |
| likely     | the rule's purpose covers the check, its text does not name it |
| unsure     | a guess; another rule may fit better                           |

## Review 2026-11-09

Four points checked at the code; each row they change is marked `R` in the table below.

1. **A check that could not run is no violation.** `labkit/checks/code_check.py:387` reports that the quality-check read check stopped on an error; `labkit/checks/prompt_check.py:216` that a prompt expression cannot be computed statically — a valid dynamic prompt warns too. Neither shows a violation; both name the check they leave open ("Checks left open" below).
2. **Data sources fall under the general freezing rule.** `labkit/checks/run_record_check.py:570` compares every source given as `data=`, inside the repository or not, not only `data/prepared/`; LAB-041 Generate numbers, don't retype them says "Freeze data sources via `runlog.run(..., data={...})`" (`labkit/docs/standard.md:288`). Its neighbour `:527` (a run that froze no source) takes the same rule. LAB-058 `data/prepared/` is read-only after writing stays for a finding that shows a change to prepared data.
3. **The adoption rule where its text names the hold.** LAB-104 A number leaves the area only through its adoption: it requires that a report's result blocks show the run the protocol adopted and equal its rendering, and that every cited run id names a run of the repo. So `labkit/checks/report_blocks.py:283`, `:293`, `:301`, `:310`, `:359`, `:367` and `labkit/gates/report_hold.py:508` take LAB-104 A number leaves the area only through its adoption, not LAB-041 Generate numbers, don't retype them or LAB-043 Runs go through `runlog`.
4. **A forwarded message gets the rule of its cause.** The recomputation (`02_analyze.py --check`, `labkit/checks/recheck.py`) forwards different causes: `:72` a protocol head that does not parse and `:96` a run config that does not parse (a check left open), `:83` the reason a run was not chosen (pass-through), `:168` a promise block that does not parse (a check left open), `:171` promises changed since the run (LAB-003 No run without an intent paragraph), `:145` a declared scope changed since the run (LAB-103 The audit reads by declared scope, not by import graph, as finalize's same check). A message of the form `{exc}`, `{gap}` or `{why}` gets a rule only after its causes are read.

## Traced to the condition 2026-11-09

The rows left likely or unsure, and every forwarded message, were followed into the function that tests the condition. A site whose sources hold different rules names each (`LAB-a/LAB-b`). In this inventory the site counts under each of them; in a usage round a message counts only for the rule of the source that wrote it — one warning of `finalize.py:287` is one rule's, never three. So when the rules move into the code, each message carries its rule where it is built.

Decided 2026-11-09:

1. **The protocol id is a technical contract, not a rule.** The binding of runs to a protocol by its id stands in the code and in `docs/protocol-run-binding.md`; LAB-043 Runs go through `runlog` is not read beyond its text. A rule follows only if people or agents need it as a working requirement. Rows: `labkit/checks/recheck.py:74`, `labkit/gates/finalize.py:192`, `labkit/formats/protocol_history.py:251`, `labkit/formats/protocol_history.py:265`.
2. **Changed records are a rule candidate, open.** `labkit/formats/evidence.py:375`: change_findings: committed evidence changed against HEAD beyond what labkit writes — a record beyond its decision lines, an audit file labkit writes once, a closed run's files; labkit's own first version passes. The message names the change it found, not who made it. Before a rule: which changes stay allowed (the decision lines are, already) and what use it has beyond the check.
3. **A head table that does not parse is a form error, LAB-011 Required-field check.** Only a table that reads can be checked for what it holds; a file that cannot be read leaves the check open. Rows: `labkit/gates/finalize.py:880`, `labkit/gates/finalize.py:967`, `labkit/gates/report_check.py:632`, `labkit/checks/recheck.py:72`, `labkit/checks/recheck.py:168`, `labkit/gates/report_hold.py:996`, with `labkit/gates/finalize.py:652`, `:667` and `labkit/gates/report_replacement.py:61` already there.

## Checks left open 2026-11-09

What each site's handler catches, read in the code: `L` a limit of the check, `A` access or environment, `M` a required file missing, `F` an invalid format. Two statements stay apart: the defect, when there is one, and the check it leaves open. The Rule column of these rows names the check left open. The duty a defect breaks is a rule where the rule's text requires the input, and labkit's technical contract otherwise; it is not taken from the check it stops, nor from labkit writing the file. A defect held only by the technical contract is still a determined defect — neither uncertain nor, by that alone, a gap in the rules. No new rule candidate follows from these rows: technical input requirements need no lab rule of their own, and "unchanged" is the open candidate's question already. The error classes mix the kinds at their source: `runs._json_of` turns `OSError` and `JSONDecodeError` into one `ArtefactError` (`labkit/formats/runs.py:350`), `scope_sha.read_source` and its parser turn a gone file, a non-UTF-8 file and a syntax error into one `SourceError` (`labkit/formats/scope_sha.py:85`). Until they tell the kind, the mixed sites cannot be counted as defects or as checks not executed.
