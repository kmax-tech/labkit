# Pin route: the run record pins a source outside git

2026-11-06. Built after release 0.112.0 (see `CHANGELOG.md`, Unreleased); the draft for decision (b) of 2026-11-05 follows ([One explainer](2026-11-04-one-explainer-plan.md), "Decided 2026-11-05"), with the author's decisions of 2026-11-06 on it; no code changed. Baseline `76757ed9`. Built after release 0.112.0, once the record check below has run.

## Problem

A source the run read that git does not track blocks `finalize` (station 5, `check_provenance`) unless one of three routes pins it. Each route is a format the agent can get wrong:

1. **Tracked in git** — right for small inputs that may legally be shared, impossible for a model directory of several hundred megabytes.
2. **Its checksum in Data / scope** (`run_record_check.pinned_source`) — the agent learns the checksum only after the run, and writing it into Data / scope then is a change to a registered field after the first measurement, which the registration hold refuses (area 19's finding).
3. **A tracked `MANIFEST.sha256` at or above the source** (`_source_manifests`, `_manifest_finding`, `formats/data_manifest.py`) — a third format; a manifest written inside the source directory changes the directory's digest, so the run no longer matches its own record (tsts512-r1).

Evidence: in area 23 of labkit-paper the first hold of all three sts512 attempts was the model directory `benchmark/models/all-MiniLM-L6-v2`, untracked and excluded by the sandbox repo's `.git/info/exclude`; none of the three found a route, all three handed over without a number. Area 21's adopted sts512 agents wrote a manifest.

## Decided

**2026-11-05:** one route, the run's own record. `runlog.run(..., data={...})` already writes the sha256 of every source it read into the record; the record is committed, and `finalize` compares the bytes now with it. The checksum in Data / scope and the manifest go (Breaking). How to get the data back (source or access route, version) stays prose in Data / scope, as the standard's Fixed inputs say — a hash alone brings no data back.

**2026-11-06 (author, on this draft):** the record is the one integrity evidence; git status is a hygiene rule beside it, not a second proof. Four parts, one duty each:

| Part         | Answers                                                                                           |
|--------------|---------------------------------------------------------------------------------------------------|
| Run record   | which bytes the run read (the sha256)                                                             |
| Data / scope | where the data come from and how to get them again (prose)                                        |
| Git          | which data belong to the versioned project: tracked, or kept outside on purpose by an ignore rule |
| `finalize`   | whether that evidence is complete and consistent                                                  |

The rule per source the run recorded:

- tracked in git → passes when its bytes give the recorded sha256;
- ignored by git (`.gitignore`, `.git/info/exclude`) → passes when its bytes give the recorded sha256;
- untracked and not ignored → blocks, even when the sha256 matches: commit it, or ignore it on purpose;
- gone, or bytes unlike the record → blocks.

No new pin file, no replacement for the manifest, no switch: the rule follows from the existing record and git status alone. The build comes after release 0.112.0, as a Breaking change of its own.

The standard needs no change: Fixed inputs already says "the repository holds instead their source or access route, version and checksum (the run records each read file's checksum, `data=`)" (`labkit/docs/standard.md:126`).

The tracked case's comparison is new: it makes "the record is the one integrity evidence" hold for every source, not only the ones outside git. Its consequence: a tracked prepared file regenerated after the run blocks until it is restored or the run is measured anew — the number came from other bytes.

What the guaranteed tier then states: the bytes the number came from are the bytes on disk now, checked against a committed record, and data kept outside git are kept there by a visible rule. What it does not state: that someone else can get those bytes back. That stays with Data / scope's prose and the agent audit, as it already is today.

## Tests and probe

Twins in `tests/test_finalize_provenance.py`, each seen red on the old code where it changes behaviour:

- an ignored source with a recorded sha and unchanged bytes, Data / scope without the sha, passes (red today); its twin with one byte changed blocks;
- the same source untracked but not ignored blocks with "commit it, or ignore it on purpose", although the sha matches;
- a tracked source whose bytes changed since the run blocks (red today); unchanged, it passes;
- a source missing from `data=` blocks with "pass it in `data=`";
- a `MANIFEST.sha256` beside an untracked file pins nothing (the manifest is not read);
- an ignored source that is gone names the route in Data / scope.

Probe: a case in the repair-path probe (`labkit-evidence`, `run-all.sh`) with an sts512-like model directory excluded by `.git/info/exclude`: measure, adopt, commit — no hold on provenance, and the record and report go in one commit.

## Check before building: the record's lifetime

The route rests on one invariant: a finalized run carries its integrity evidence with it — the committed record — or `finalize` fails. No silent success without a record. The 2026-11-05 decision says the commit holds until the record comes with it (fix 1, `12ee8eb6`); that has not been reproduced for this case. Before building:

1. measure a run;
2. commit the report citing it without `runs/<id>/`;
3. in a fresh clone of that commit, run `finalize` and `report-check`;
4. see whether they fail with a sentence that names the missing record — or whether the commit already refused step 2.

If the commit refuses step 2, or the fresh clone fails loudly, a regression test holding that is all this check adds; no further architecture. If either passes silently, the hold that refuses a commit citing a run whose record the index lacks is part of this step.

**Result (2026-11-06, on the stamped count task, labkit at `6363d233`):** both hold, nothing passes silently. The commit of protocol and report without `runs/<id>/` is refused by the hook ("the working tree differs from the index", naming the run's files). With `runs/` ignored by a `.gitignore`, the hook refuses as well ("git ignores it — evidence labkit wrote that no commit can carry"); that hold comes from `evidence.ignored` alone — with it disabled, the commit passes. A commit made past the hook (`--no-verify`) fails loudly in a fresh clone: `finalize` names no completed run, `report-check` names "cites run … no runs/<id>/ in the repo". The regression test is `IfReported.test_a_commit_without_the_adopted_runs_record_is_held` in `tests/test_report_check.py`, seen red with `evidence.ignored` disabled; no further architecture.

A second limit, kept as a known one: a directory source's digest covers every visible file, so any file added under the model directory after the run (a README, a cache) changes the digest and blocks with "restore or measure anew". The manifest route had the same limit (tsts512-r1); the hold's wording should name the added file where the record allows it, else the field guide states the limit. The record keeps no file list, so the field guide states it (Data / scope).
